### 2.2 动作（46 个，30fps，全部 in-place）

**对「走路」有用的只有这些**：

| 类别 | 动作 | 帧数 | 时长 |
|---|---|---|---|
| 站立 | `idle1` / `idle2` / `idlein` | 66 / 221 / 142 | 2.2 / 7.4 / 4.7 s |
| **位移** | `run` / `run_fast` / `run_homeguard` / `run_homeguard_runin` | 36 / 40 / 40 / 76 | 1.17 / 1.30 / 1.30 / 2.53 s |
| **原地转身** | `turn0` / `turn_l` / `turn_r` | 16 / 14 / 14 | 0.50 / 0.43 / 0.43 s |

**⚠️ 没有 `walk`。** 其余 39 个是攻击/技能/表情/死亡/回城。

**由「没有 walk」推出的两条结论**：

1. 走路只能**用 `run` 放慢**。`run` 一个循环 1.1667 s 是两步 ⇒ 步频 1.71 步/s。
   若想让 1.85 m 的角色以约 1.2 步/s 走路（步幅 ~0.75 m ⇒ 移速 ~0.9 m/s），
   播放速率约 **0.70**（时长拉到 ~1.67 s）。**这是一个可算的数字，不需要猜。**
   （LoL 里 Darius 没有独立行走动画，只有奔跑；放慢是最常规的做法。）
2. 源动作**全是 in-place**（不含位移），所以速度必须靠**代码里的 `MaxWalkSpeed` + Stride Warping**
   去匹配，不能指望动画自带位移。这正是 G3b 门禁要卡的东西。

### 2.3 风格（会直接影响「走路像不像」）

- 为**俯视角可读性**服务：整体前倾、幅度夸张、常有「两个姿态」的极简帧。
- 实测偏离 bind pose 的角度（详见 `FINAL_Retarget_Plan.html`）：
  `idle1` 颈段 −32°；`run` 躯干 +34°、颈 +52°；`run_fast` 躯干 **+62°**、颈 +64°。
  ⇒ **`run` 是大幅度前倾**，直接搬到第三人称会像「弯腰冲刺」。这是 M1-④ 去倾斜要处理的，
  但它**不影响「能不能走路」这一步**——先能动起来，再谈好不好看。

### 3.2 🔴 那个 100× 是关键矛盾

**两套骨架的最外层都有 scale = 100**，而它们的骨骼局部平移都是「已经除以 100」的单位：

```
源 ： skinned_mesh(×100) → Root → Pelvis → …
目标： darius_godking_mesh_LOD0_Skeleton(×100) → root → pelvis → …
```

⇒ 目标 `pelvis` 的**局部**平移**必须**是 `1.0967`，出去经 ×100 才是 109.67 cm 的正确髋高。

**而重定向器写进去的是 `109.6706`** —— 正好是「厘米值」写进了「除以 100 之前的槽位」，
出去又被 ×100 ⇒ 世界 10,967 cm。**整条骨架被这一根骨推到离原点 ~147 米，所以预览全空。**

22 根关键骨逐根比对：**21 根精确等于 rest（比值 1.00），只有 `pelvis` 一根是 ×100。**

## 4. 三者交汇出的核心矛盾

**这不是「哪个设置填错了」，而是两种骨架约定在一条边界上撞车。**

1. **源没有二段缩放**：源骨架可以看成 `skinned_mesh(×100) → Root → 一切`，中间只有一个 `Root`。
2. **目标多一层**：目标在 ×100 和 `pelvis` 之间还插了一个 `root`。
3. **retarget root 取的层级不同**：源取 `Root`（≈髋高 51%），目标取 `pelvis`（59%）。
   两者语义接近但不完全同层。
4. **重定向器写 retarget root 的平移时，没有把祖先骨的 ×100 算进去**（实测结论），
   于是这一根骨的平移是「厘米值」。

**可证伪的推论**：如果问题真的只出在「retarget root 的平移 + 祖先缩放」这一处，
那么**只要把这一根骨的平移修对，其余 21 根骨本来就是对的**，动画立刻就能看。

**风险（必须在重新规划里承认的）**：

- **`Spine` 链骨数不等**：源 2 节（`Spine1→Spine2`）vs 目标 3 节（`spine_01→spine_03`）。
  未验证过这会不会引入躯干偏差。
- **24 根 twist 骨无人驱动**：源骨架里没有任何 twist 骨，重定向后它们只能保持 rest。
  走路时大腿/小腿/手臂的扭转会「不跟手」，表现为**扁平、像棍子**。
  这是「像不像」的长期问题，不是「能不能动」的当前问题。
- **身高/髋高比例差 ~7%**：源髋高 51% vs 目标 59%（颈长 +84%、髋宽 −22% 已知）。
  走路时脚会不会浮空/穿地，需要实测（G2/G3a）。

## 5. 三个候选修法（按代价从低到高）

### 选项 A —— 后处理把 target root 的平移写回 rest（**推荐先做**）

- **做法**：重定向后，用 `Skeleton.get_reference_pose()` 读 rest 平移，
  把输出 `AnimSequence` 里 `pelvis` 的平移曲线**逐帧写回 rest 值**。
- **合法性**：源动作本来就是 in-place，pelvis 的局部平移在源里逐帧几乎恒定
  ⇒ **写回 rest 不损失任何有效信息**；缩放因子是从资产**读**出来的，不是手填魔数。
- **代价**：小。只需一个脚本 + 复测。
- **验收**：`ik_16` 的 pelvis 比值回到 **1.00**，且 Persona 里肉眼可见角色站在原点附近。
- **局限**：这是**治标**。将来如果要 retarget 带位移的动作（跳跃、击退），这条路会挡住。

### 选项 B —— 改 retarget root / 加 pelvis 链（**值得先花 10 分钟试一次**）

- **做法**：把目标 IK Rig 的 retarget root 从 `pelvis` 改成 `root`，
  并给两边各加一条 `Pelvis` 单骨链，让 `pelvis` 变成**普通 FK 骨**。
- **依据**：另外 21 根骨走的正是 FK Chains 路径，`translation_mode: None`
  ⇒ **平移精确等于 rest（比值 1.00）**，已被数据证明。让 pelvis 走同一条路，理应得到同样结果。
- **代价**：中。改 retarget root 可能影响 9 条链配对，改完必须重跑 `ik_06_verify_map.py`。
- **风险**：FK Chains 只负责旋转与「保持 rest 平移」，**骨盆的上下起伏可能一起丢失**。
  对走路来说起伏其实是加分项（可后续用曲线补），对「能不能走」无影响。

### 选项 C —— 重导目标模型，把 100× 从骨上拿掉（**治本，但代价大，建议留到 M2**）

- **做法**：以正确的 `convert_scene_unit` / `import_uniform_scale` 重新导入 `SK_Darius_GodKing`，
  让最外层骨 scale = 1，尺寸靠 mesh 自身承担。
- **收益**：100× 这个「陷阱源」彻底消失，以后所有重定向/武器/物理都不用再打补丁。
- **代价**：**武器 socket 契约要重标定**（`relative_scale = 0.01` 就是为它准备的），
  还要复核描边壳、材质槽、`BP_DariusCharacter` 里所有依赖尺寸的地方。**这是一次大手术。**
- **结论**：现在**不做**。写在这里是为了让将来的自己知道这条路存在。

## 6. 重新规划：最小可行路径（M1'）

目标：**握斧走路跑起来。** 每步都有可复现的数字验收，过不了不进下一步。
