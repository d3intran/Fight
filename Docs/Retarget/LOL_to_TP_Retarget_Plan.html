LOL 俯视角原版动画 → 2XKO 第三人称模型 · 重定向实施计划

Fight 项目 · 2026-09-18 · 目标：动作「自然」而非「能播」｜配套已有资产审计数据与外部调研
核心判断（先看这段）：
① 技术上完全可行，但「自然」的瓶颈不在重定向算法，而在三件事：风格去 MOBA 化、比例各向异性补偿、足部接触一致性。
② 现有自研 Blender 管线（几何帧 + K 基准补偿，均值 9.7°）已经把「骨骼朝向」这件事做到了可用，建议保留作为离线批处理与验证器；
③ 但主力应当切到 UE5 IK Retargeter——它自带 Retarget Pose 对齐、IK Goals、Chain Scaling、Stride Warping、Speed Planting 这五件我们正在手工重造的东西，而且是 Epic 在维护。
④ 另有一条降维打击路线：2XKO 本体是可解包的 UE5.4 工程，Darius 的第三人称导航动画（darius_base_nav_std_*）真实存在。用官方同源动画做 locomotion、LOL 动画做技能，是最快达到「自然」的组合。

1. 两侧模型/资产的真实特色（本次实测数据）

1.1 源：LOL 原版 Darius（skin15 神王）

项目实测值对重定向的影响

2. 外部调研结论（可参考的案例 / 经验 / 规则 / 工具）

2.2 社区/官方沉淀的规则（直接可用的经验法则）

Riot 侧（风格）：
  • 「为了清晰度，League 的俯视角动画会夸张动作并倾斜模型（tilt models）以提升可视性」；招式常用「两姿态 + 强剪影」，靠 timing texture（非对称节奏）表达重量。
  • Riot 用 Maya + 组件化 rig（手臂/腿/脊椎/披风都是可复用 component）+ Jiggle（自动次级运动）+ "space switcher"（道具手部空间切换）。
Epic 侧（重定向）：
  • Retarget Pose 对齐是最高频的失败点：源 A-Pose、目标 T-Pose 时若不对齐，"the majority of visibly broken retargets" 都源于此。
  • FK Translation Mode 用 Globally Scaled 而不是 Absolute/None：按源/目标骨长比缩放，保留目标自身比例，否则目标会被源的比例"拉长压扁"。
  • 腿链只定义到踝（Ankle），不要连到脚掌球（ball）；Chain Depth = 2。
  • 滑步标准解法：源动画加 MotionExtractorModifier 生成每只脚的速度曲线 → IK Retargeter 上开 Speed Planting，Speed Threshold 略高于曲线平坦段。
  • 骨盆权重规律：Pelvis 的 Blend to Source Translation = 1.0，但把其 Z 分量权重设为 0；腿部 Blend to Source 设 1.0。
  • 目标多出的 twist 骨：源没有对应时，用 Twist Corrective / Bone Driven Controller 由腕/肘的 roll 驱动，而不是硬映射。
  • 若源骨架有 virtual bone/VB_ 骨而目标没有，IK 会在引擎里悄悄偏移。

3. 技术路线选择

方案做法优点缺点评估
A. 纯 UE IK Retargeter 把 LOL 骨架 + 动画导入 UE 作为 source（GLB→FBX 或直接 FBX）→ 建 IK Rig ×2 → IK Retargeter 映射 + Retarget Pose 对齐 + Speed Planting → 批量导出 Sequence 工具官方维护；自带比例缩放/IK Goals/滑步修正；批量；结果直接是 UE 资产 源骨架 179 骨（含王座/狮子）需要在 UE 里裁剪；骨架朝向差异要靠 Retarget Pose 手工掰 主力推荐
B. 强化现有 Blender 自研管线 在 v4 基础上：换 Aventurine 原生 .anm 输入 + 分链缩放 + 逐关节偏移 + twist 程序化 + 关节点误差验证 已有 9.7° 基础；完全可控；可脚本化反复跑；Cascadeur 可作后续清理 要自己重造缩放/滑步/IK；每一项都有踩坑成本；不如 A 稳 备选 / 离线批处理
C. 混合（降维打击） locomotion（idle/walk/run/turn）用 2XKO 官方动画，LOL 动画只用于技能/表情/舞蹈 同源骨架 → 零重定向误差、零滑步、零风格冲突；开发时间从周级降到天级 需要解包 2XKO 本体；偏离"用 LOL 动画"的原始意图（但 locomotion 本来就不是 LOL 的强项） 强烈建议并行验证
推荐组合：C 打底 + A 主力 + B 兜底。 先用 C 花半天验证 2XKO 官方 locomotion 是否可得（这是最高性价比的一步）；同时按 A 建设 LOL 动画的完整重定向管线； B 保留作为「离线批量处理 + 客观验证器」——因为 blender_80_orient_verify.py 这套度量是 UE 里没有的，验收还得靠它。

4. 实施计划

阶段 0 · 基线与验收体系（先建尺子，再动手）

动作
  1. 冻结当前状态：把 /Game/Character/Darius/Anims/ 里 8 支偏斜动画（v2，26.8°）标记为废弃（移到 _Deprecated/，不删）。
  2. 新建两个与先验假设无关的验证器（现在的 blender_80 只验朝向，不够）：
    • blender_90_joint_pos_err.py：缩放归一化后的逐关节世界位置误差（mm）——「像不像」的最终判据。
    • blender_91_foot_contact.py：输出每帧左右脚的高度+水平速度曲线，判定支撑相/摆动相，统计支撑相水平漂移与触地时刻差。
  3. 标定源动画的隐含速度：blender_92_stride_speed.py 用「支撑相脚相对骨盆的位移 × 帧率 / 周期」算出 run/idle 的地面速度（cm/s），写进计划表。
验收：跑出三条基线数字（当前 9.7°/滑移未知/速度未知），存 Docs/Retarget/baseline.json。

阶段 1 · 源侧资产规范化（1~2 天）

动作
  1. 试装 Aventurine（Blender 5.2 兼容性实测）。成功则改走原生 .anm 读入；失败则保留 lol2gltf → GLB 路径（已可用）。
  2. 写 plan_10_src_clean.py：白名单裁剪源骨架——只保留 Root / Pelvis / Spine1 / Spine2 / Neck / Head / L·R_Clavicle / L·R_Shoulder / L·R_Elbow(Upper) / L·R_Hand / L·R_Hip / L·R_KneeUpper / L·R_KneeLower / L·R_Foot / L·R_Toe / Cape 链， 删除 Lion_* / Throne / Gem / Piece_* / *Buffbone*。
  3. 修正「微骨陷阱」：把踝点重定义为 L_KneeLower.tail、趾点用 L_Toe.head 的投影到脚掌平面结果，写成一份 joints_src.json（与骨骼内部朝向解耦）。
  4. 导出「干净源骨架 + 全部动作」FBX（30fps 帧边界对齐）。
验收：源骨架骨数从 179 降到 ~45；FBX 重新导入 UE 后动画总时长与源逐帧一致（帧数偏差 0）。

阶段 2 · 目标侧 IK Rig + Retarget Pose 标定（1 天）

动作
  1. 在 UE 里建 IKR_Darius_2XKO：链 = Spine(pelvis→spine_03) / Head(neck_01→head) / 左右 Arm(clavicle→hand) / 左右 Leg(thigh→foot，只到踝) / Root(pelvis 单选)。
  2. 加 IK Goals：IK_Foot_L/R、IK_Hand_L/R；Leg 用 Limb IK 解算器，Chain Depth=2。
  3. 为源骨架建 IKR_LOL_Darius，同样结构（源的膝盖 Upper/Lower 双骨只用 L_Hip 与 L_KneeLower 进链）。
  4. 建 RTG_Darius，映射链，进 Edit Retarget Pose 手工对齐两侧 A-Pose。
验收：Retarget Pose 对齐后，源与目标的肩、肘、髋、膝、踝 6 组关节在预览视口里重合度 < 2cm（用 Measure Tool 量）；对照 blender_90 的关节位置误差基线应显著低于 9.7° 方案。

阶段 3 · 比例三层补偿（2 天）—— 「不夹腿、不浮头」的关键

动作
  1. 第一层 全局：Retarget Root 的 Scale / Translation 用 Globally Scaled（自动 0.009883 → 1.0 世界）。
  2. 第二层 分链：
    • Leg 链：勾 Chain Scaling，Scale Factor 取实测腿长比 0.0094/0.009883 = 0.951（即目标腿短 4.9%，让步幅自动缩短）。
    • Arm 链：关掉 Chain Scaling（臂长比已匹配 0.0099≈全局）；改用 Rotation Offset 修正肘点前后错位（上臂 −12% / 前臂 +15%）。
    • Spine：关闭缩放（脊柱比 0.0103 已接近 1，强制缩放会让胸廓变形）。
  3. 第三层 逐关节（本项目特有，必须做）：
    • 髋宽 −22%：给目标 thigh_l/r 加固定的外展偏移（绕前后轴 +6°~8°），把腿的起点"撑开"，否则走路膝盖会互相挤。这个值用「让目标两膝间距与源的两膝间距在直立帧相等」反解出来。
    • 颈长 +84%：对 neck_01 的平移通道不做重定向（只搬旋转），并给 head 一个固定下压偏移，让头顶高度与源按比例一致。
验收：blender_90 关节位置误差（归一化到身高）中位 < 1.5%、P90 < 4%；直立帧的两膝间距 / 身高 与源偏差 < 5%。

阶段 4 · 足部接触与滑步治理（2 天）

动作
  1. 源动画加 MotionExtractorModifier（bone = ball_l/ball_r，Motion Type = 平移速度，Axis = XYZ）→ 生成速度曲线。
  2. IK Retargeter 腿链开 Speed Planting，Speed Threshold 取曲线平坦段之上略高值（先取 30，按曲线实调）。
  3. UE 侧全局：IK Asset 用 Full Body IK，Sub Iterations = 10，Root Behaviour = Free，Global Pull Chain = 0.0；髋骨 Rotation Stiffness = 1.0。
  4. Retarget 里 Pelvis 的 Blend to Source Translation = 1.0，但 Z 分量权重 = 0；腿链 Blend to Source = 1.0。
  5. 步幅—速度闭环：把阶段 0 标定的源隐含速度与目标动画重算速度对齐——若目标动画隐含速度 = V_anim，则设 CharacterMovement.MaxWalkSpeed = V_anim（或反过来对动画做 stride warp）。两者必居其一，别两边都凑。
验收：blender_91 支撑相脚掌世界坐标水平漂移 < 2cm；动画隐含速度 vs 引擎移动速度误差 < 5%（跑动全程肉眼不可见滑步）。

阶段 5 · 风格去 MOBA 化（3 天）—— 「自然」的主战场

这是整个任务里没有现成工具、必须自己定标的部分。Riot 的动画本来就为俯视角做了艺术妥协，直接搬到第三人称一定"不对劲"。
动作
  1. 去前倾（de-tilt）：blender_93_lean_audit.py 逐帧测「骨盆→胸的躯干轴 vs 世界竖直」夹角，得到源的恒定前倾基线 θ_src（估计 8°~15°）。重定向时在 spine 链上叠加 −θ_src × 权重 的反向俯仰（现有 SPINE_PITCH 参数就是它的雏形，要升级成"按实测基线自动求解"而不是手填）。
    验收：Idle 帧躯干前倾角落在人体自然站姿 2°~6°。
  2. 幅度收敛：对超出生理限位的关节角做软压缩而非硬截断： θ' = θ_lim + (θ − θ_lim) · tanh(k(θ − θ_lim)) / k，保证 C¹ 连续不产生抖动。幅度整体收 10%~25%（按关节分别定）。
    验收：膝/肘/肩任一帧不超过生理限位（膝 0~150°、肘 0~145°、踝 −30~50°）；且总幅度保留 ≥ 75%（保留角色性格）。
  3. 解两姿态感：对「姿势之间几乎线性插值」的段落做时间重分布：在接触/发力帧用 ease-out 聚拢、在过渡段拉开，人为制造 timing texture。
  4. 次级运动（这是"自然"的最大加分项）：

    • 肩甲狼头/披风/斧头挂饰做一阶滞后（overlap）滤波。
    • Aventurine 的 Wiggle 2 物理或 Cascadeur 的 Secondary Motion 滑块可直接产出这段数据。
    验收：百帧慢放无明显"整块刚体"感；转身时披风滞后 2~4 帧。
  5. twist 骨程序化驱动：lowerarm_twist_01/02/0x_l 由 hand_l 相对 lowerarm_l 的 roll 用插值驱动（不要直接映射，源侧没有）；thigh_twist_* 由髋旋转的 30%~50% 驱动。用 Twist Corrective 或 Bone Driven Controller 节点。

5. 关键难点与对策

#难点为什么难对策
D1两套 A-Pose 基准差（前臂 39°、锁骨 43°、骨盆 41°、脚 119°） 旋转增量法只能搬增量，搬不动基准差；整矩阵对齐会因滚转参考差 180° 把骨翻转 已有解：逐骨骼最小弧旋转 K（blender_51_retarget_v4）；UE 路线则用 Edit Retarget Pose 可视化对齐。两条路都要保留 K 的量化输出做对照
D2膝/肘的 Upper/Lower 双骨导致三点链退化 源 L_Hip 与 L_KneeUpper 等长且共线，几何帧的 z 轴（cross(y, c−b)）会趋零 → 腿部误差最大到 63° ① 链里只用 L_Hip 与 L_KneeLower；② 退化时回退到「上一帧的参考平面」而不是全局 Z（避免帧间跳变）；③ 对腿部改用 IK 目标解算而不是纯 FK
D3比例各向异性（髋 −22% / 颈 +84% / 腿 −4.4%） 全局缩放只能解决一个自由度 三层补偿（阶段 3）；髋外展偏移与头下压偏移用反解求得而不是手调
D4俯视倾斜与夸张幅度 这是艺术意图，不是误差；不能靠算法"修"，必须定标后再改 先量化（前倾角、关节极值分布），再按固定策略去倾斜 + 软压缩；保留至少 75% 原始幅度
D5目标侧 24 根 twist 骨无源 硬映射会让前臂/大腿「糖纸扭曲」；留参考姿态则完全不跟随 程序化驱动（Twist Corrective / Bone Driven Controller），由腕/髋 roll 按比例带动
D6武器在源里是独立骨子树 LOL 动画里 Axe_Handle 独立于手；目标是把斧头 socket 挂在手上，两者握持关系可能不一致 先测量「源 R_Hand 到 Axe_Handle 的相对变换在整段动画里的漂移量」。若漂移小（刚握）→ 直接用 socket；若漂移大（换握/脱手）→ 需要把斧头单独挂到 weapon_jnt_r 并重定向武器骨
D7LOL 没有 walk 动画 BlendSpace 需要 walk；源只有 run / run_fast / run_homeguard ① 从 run_fast 做时间拉伸 + 重新踩点得到 walk；② 或从 2XKO 官方 nav_std_walk_forward 取（方案 C）
D8面部/披风骨无源 目标 ~150 面部骨 + 披风链，源只有 3 段 Cape 面部留参考姿态（后续用 Morph/Control Rig 单独做）；披风把源 3 段映射到目标披风链前 3 节，其余节由物理/弹簧跟随

9. 需要你拍板的点

  1. 路线：是否接受「C 打底（2XKO 官方 locomotion）+ A 主力（LOL 动画走 UE IK Retargeter）」？还是坚持全部用 LOL 动画？
  2. 风格改造的力度：允许把 LOL 的前倾和夸张幅度改掉多少？我建议「去倾斜 100% + 幅度保留 75%」起步，但这是艺术决策。
  3. 步幅策略：改动画（stride warp）还是改引擎速度（MaxWalkSpeed）？我建议改引擎速度——动画更保真，且后续加技能位移时更灵活。
  4. walk 动画来源：LOL 没有 walk。是从 run_fast 降速重采样，还是用 2XKO 官方的 walk？
  5. 是否动资产：阶段 3 的髋外展/颈下压偏移可以写在 socket/Control Rig 层（不动资产），也可以写进骨架（更彻底但动资产）。我倾向先写在 Control Rig 层，定稿后再考虑固化。
  6. Cascadeur 是否值得花钱：Indie $19/月能给 FBX 导出与脚部物理清理。若阶段 4/5 手工调耗时超过 2 天，性价比就成立。
