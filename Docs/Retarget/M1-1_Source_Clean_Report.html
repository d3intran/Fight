2.3 用世界矩阵回写补偿消失的父级贡献

删掉 L_KneeUpper 后 L_KneeLower 的父级换了，它的局部变换语义随之改变。 不做处理会引入约 8.94 单位（≈9 cm）的位置错误。补偿方式不是手推四元数公式，而是：

  1. 采样：净化前，遍历全部 46 个 action 的每一帧，记录 L_KneeLower / R_KneeLower / L_Elbow / R_Elbow 的 pose_bone.matrix（armature space 4×4）。
  2. 手术：重挂父级 + 删除 120 骨。
  3. 回写：逐帧把采样到的世界矩阵写回，并用 keyframe_insert 同时写 location / rotation_quaternion / scale 三个通道。
为什么用「世界矩阵采样-回写」而不是解析公式：解析公式要正确推导 Blender 的 pose_matrix = parent_pose @ rest_rel @ matrix_basis 三级关系，任何一处符号错误都很难自查。 而 pose_bone.matrix 的 setter 会自己反解 basis —— 用「把世界矩阵摆回原位」这个 物理上可验证的目标替代公式推导，正确性由 §3.2 的逐帧回归保证，而不是由推理保证。
踩坑记录：回写时最初漏了 scale 通道，导致 4 个动作出现 0.0135 单位的位置偏差。 虽然事后证明该偏差另有来源（见 §6），但 三通道必须一起写 —— 源动画确实存在骨骼缩放通道。

四、★ 关键发现：三个「静默毁掉交付物」的陷阱

这三条的共同特征：不崩溃、不报错、产出物看起来正常，但拿到下游就不可用。 它们只能被「跨会话 + 最终消费者」这两层验证抓到 —— 这正是为什么验收必须做到 L3 / L4。 三条都是本轮实际踩到并修掉的，其中两条还影响项目历史上的既有脚本。

4.A 陷阱一：FBX 导出前未把 armature 复位到 rest pose

这是本轮收益最高的发现。它不只是一个「脚本 bug」，而是项目历史上所有逐动作导出脚本的系统性缺陷。

4.1 现象

第一版净化脚本三层验收里，L1 / L2 全 PASS，但 L3 报出：FBX 的 matrix_world 是单位阵，而骨骼 head 本身整体错位：

关节源 GLB（rest）错误 FBX偏差
R_Hand(68.93, 0.37, 128.29)(37.38, 40.48, 99.66)58.52
L_Shoulder(-23.34, 12.11, 178.50)(-8.46, -15.70, 166.22)33.85
Root(0.00, 0.00, 127.37)(14.92, -13.34, 121.87)20.75

骨骼关节间距也随之变化 2~4%（肩宽 −2.0%、躯干链 −3.9%）—— 这不是数值噪声，是形状改变。

4.2 根因

净化脚本在导出前刚跑完「46 个动画的逐帧验证」循环，此时 armature.animation_data.action 还挂着最后一个动画，frame 停在最后一帧。Blender 的 FBX 导出器会把当前 pose 写成骨架的节点变换，而不是 rest pose。

4.3 影响面（已排查项目全部导出脚本）

脚本有无复位判定
blender_51_retarget_v4.py（重定向正式版） 第 286 行设了 action = None，但循环内第 289 行又把它挂回去，且循环里没有 frame_set 中招
blender_30_batch_retarget.py同模式中招
blender_50_retarget_v3.py同模式中招
blender_10_retarget.py同模式中招
blender_21/22_strip_*.pybake_anim=False（不导动画）不受影响

也就是说，之前导入 UE 的每一批重定向动画，其 Skeleton 的 bind pose 都是某个动画的某一帧， 而不是静止姿态。IK Retargeter 会用这个错误的 bind pose 建立骨骼参考系 —— 这足以单独造成显著的系统性角度误差，很可能是 26.8° 翻车事件的一个共因。

4.4 修复

# 导出前：断开 action 并清空全部 matrix_basis
if arm.animation_data:
    arm.animation_data.action = None
for pb in arm.pose.bones:
    pb.matrix_basis = Matrix.Identity(4)
bpy.context.view_layer.update()

修复后 L3 全部转为 PASS（§3.3）。脚本内加了 rest 自检：

rest 自检：Root.head_local = (0.0000, 0.0000, 127.3700)  [源 rest = (0.0000, 0.0000, 127.3700)]

4.B 陷阱二：纯骨架 FBX 在 UE 侧「导入成功但产出 0 个资产」

第一版净化脚本出于「IK Rig 不需要网格」的考虑，把源网格一并删掉了。结果 UE 侧：

[Info] === 开始导入 ...Darius_SrcClean.fbx ===
[Info] imported_object_paths = 0 个
[Info] 资产总数 = 0

根因：UE 的 FBX 导入需要至少一个 SkeletalMesh 作为载体，才能建出 Skeleton + AnimSequence。没有网格时它不报错，只是什么都不生成。

修复：保留源网格 Mesh_0 作为骨架载体，但

  • 清空材质槽（不导入无关贴图 / 材质）
  • 删除指向已删骨的 120 个失效顶点组（剩 59 组，与骨架一一对应）
  • 导出选择集 = armature + 该网格

代价：FBX 从 25.26 MB 增到 25.77 MB。收益：UE 侧一次导入即得 48 个资产（1 Skeleton + 1 Mesh + 46 Anim）。

4.C 陷阱三：ue_remote.py 的「.py 字样」陷阱

写 UE 侧验证脚本时，第一版 plan_14 直接执行失败：

[Error] 执行失败:
Could not load Python file 'E:/UE_5.8/Engine/Binaries/Win64/# -*- coding: utf-8 -*-
"""
plan_14_ue_import_test.py' (resolved from '...')

UE 把脚本内容当成了文件路径。二分定位（5 组对照测试）：

测试大小结果
极简脚本（无注释）40 B通过
多行 + # -*- coding -*- + docstring + 中文≈120 B通过
纯 ASCII 长脚本（60 行填充）4964 B通过 ⇒ 排除长度因素

结论：MODE_EXEC_FILE 下若向 UE 传「内容」，UE 会在内容里嗅探形如 xxx.py 的字样并误判为路径。所以只要脚本的 docstring / 注释里写了自己的文件名 （例如用法示例 ... Scripts/plan_14_xxx.py），整个脚本就静默不执行。

修复（改在网关里，而不是让每个脚本作者记住这条隐蔽约定）：

runner = os.path.join(os.path.dirname(os.path.abspath(__file__)), "_ue_remote_run.py")
with open(runner, "w", encoding="utf-8") as f:
    f.write(code)
success, logs = run_ue_code(runner)          # 一律传「路径」
if not success and any("Could not load Python file" in l for l in logs):
    success, logs = run_ue_code(code)        # 回退：传「内容」

验证：修复后原失败用例与回归用例（含中文、长 ASCII、无 .py 字样）全部通过。

五、方法论沉淀

5.1 用对照实验区分「我的操作引入的」与「工具的固有行为」

L1 报出 R_Foot 的 rest 偏差 2.68e-4 时，我先提出了一个假设： 「这是 Blender 对 0.014 单位微骨重算 roll 的固有数值不稳定」。这个假设被对照实验否证：

对照rest 偏差 > 1e-5 的骨数
A. 仅进出 EDIT mode，零修改0 / 179　否证我的假设
B. 删掉一根无关骨（Piece_1）0 / 178
C. 删 120 骨 + 改 edit_bone.parent5 / 59（R_Foot 2.680e-04 最大）

A、B 全 0 而只有 C 出现偏差 ⇒ 偏差由修改 edit_bone 的 parent 触发 Bone.matrix_local 重建所产生， 且只影响短骨。「零修改对照组」是这类归因里成本最低、判别力最强的一步—— 跑一次不到 30 秒，却把「工具固有」和「我引入的」彻底分开。

5.2 微骨的数值陷阱（可复用清单）

  • L_Foot / L_Toe 长度只有 0.01396 单位。它们的 tail 距 head 仅 0.014，(tail−head).normalized() 的相对误差被放大 ~7e4 倍 ⇒ roll 参考系不稳。
  • 因此：踝关节取 L_Foot.head，绝不取 L_KneeLower.tail；脚趾取 L_Toe.head。
  • 同理，R_Foot 的 Y 轴指向 −Z、L_Foot 指向 +Z，方向不同导致两者在重建时的数值行为不对称 （实测 L 侧偏差 2e-4、R 侧 1.3e-2，差 60 倍）。左右不对称本身就是「数值问题而非结构问题」的指纹。

5.3 验收器要「与被验证对象的先验假设无关」

弱指标（易假阳性）
  • 比较 bone.length —— glTF/FBX 对 tail 定义不同
  • 用「全部骨」的 z 范围当身高标尺 —— GLB 侧混入 Gem(z=396.8) 与 Axe_Handle(z=−90.8)，会算出 2.36 倍的假缩放因子
  • 在同一会话内自比 —— 发现不了导出/导入环节的损失
强指标（本轮实际采用）
  • 关节间距（head_local 之差）—— 缩放不变、朝向无关
  • 固定骨集合算标尺，两侧同定义
  • 跨会话：源与产物各导入一次再比
  • 逐帧世界矩阵（46×3078×27），而不是单帧抽查
