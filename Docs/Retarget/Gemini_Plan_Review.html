Gemini 重定向方案 · 技术评审

评审方式：不靠印象，用本项目已解包的源/目标资产逐条实测校准｜2026-09-18
总评：结构是这一版三份方案里最"交付化"的，可以说形式上是加分项；但它的核心机理被实测推翻，而且漏掉了比它所述更严重的问题。
① 「脊柱刻意后仰 15°~30°」——部位错、量级错。实测：脊柱在 idle 里几乎完全不动（相对 bind pose 仅 +0.4°），后仰全部集中在 颈段 −32° + 头骨 −12°（合计 ≈44°）。
② 它完全没发现在 run 家族上真正的夸张是「大幅前冲」——躯干 +34°~+62°、颈段 +52°~+64°，累计 86°~126°。这比 idle 的抬头问题在第三人称下更致命。
③ 按它给的权重（spine 30/35/25%，neck −60%）执行，在 idle 上会把本来正确的躯干推成前倾，在 run 上则是"歪打正着"地减小前倾——本质上是拿错了手术刀。

1. 实测校准：Gemini 的前提对了一半

方法：plan_03/04/05 三个脚本。前后方向先由两个独立锚点锁死——披风链在 +Y（身后）、斧刃在 −Y（身前），故 forward = −Y，不依赖任何骨骼朝向约定。倾角只用关节坐标计算。

1.2 结论

Gemini 说对的部分：LOL 确实为俯视相机做了人工畸变，而且确实发生在"抬头"这件事上（34°+ 相机俯角下要露脸，必须把头抬起来）。

Gemini 说错的部分（三处，都很关键）：
  1. 部位错。它说"脊柱链（Spine1~Neck）被刻意向后仰"。实测脊柱链在 idle 上零位移（−2.7°~+3.0°，中位 +0.4°）。后仰 100% 来自 Neck 骨本身 + Head 骨。
  2. 量级错。它说 15°~30°。实测颈段 −32°~−35°、头骨再叠加 −12°~−15°，合计 ≈44°~50°。是它估计的 1.5~3 倍。
  3. 漏掉了更严重的一半：run 家族是「前倾」不是"后仰"。run_fast 躯干 +62° + 颈段 +64° ≈ 126° 累计前冲。放到第三人称上不是"望天"，是"趴着跑、脸朝地"。这一条它整份方案零提及。

3. 方案设计上的四个实质问题

3.1 G2 门禁「视线 |Pitch| ≤ 5°」是个危险约束

逐帧强制头部前向绝对水平，会剥夺头部随动作的自然点头——跑步时头本来就应该随躯干有 3°~8° 的周期性起伏。更危险的是：如果按它自己 idlen/attack 的实测（颈段最大 +39°/+69°）去做硬约束，会在发力帧产生明显的"头部卡住"感。

修正：改成两级——① 慢变偏置消除（用低通滤波估出"俯视补偿基线"，只减去它）；② 关键帧约束（idle 站立帧 |pitch| ≤ 6°，发力帧放宽到 ≤ 25°）。指标改为「头部相对躯干的偏置在整段动画上的标准差 < 4°」——这才对应"没有卡住"。

3.2 G3 只测动画内部脚滑，测不到世界空间滑步 —— 验收门禁有真实漏洞

脚部锁地解决的是动画帧内脚掌相对骨盆的漂移。但 in-place 动画 + CharacterMovement 是两层独立速度：动画隐含速度（步幅 × 周期）与胶囊移动速度。两者不匹配时照样溜冰，而 G3 完全看不见这件事。

这意味着：按 Gemini 的门禁，一个"G3 满分但引擎里疯狂溜冰"的交付物可以通过验收。必须补一条：
G3b 动画隐含速度 vs MaxWalkSpeed 误差 < 5%（脚本从支撑相的骨盆位移推算）。

3.3 G4「左手腕与斧柄插槽 ≤ 0.5cm」过严

源骨架没有任何 IK/极向量骨（实测 twist/ik/ctrl 全为 0），目标前臂还有 2 根 twist 骨需要程序化分配。在这种条件下要求 0.5cm 贴合，实际会逼出"用 IK 硬拉导致肩肘姿势崩坏"。建议改为 ≤ 2cm，或按斧柄直径定义（贴合即"掌面与柄面接触且不穿透"），并把判据放在视觉关键帧而不是全帧。

3.4 最大的战略性缺失：没用目标骨架的最大优势

2XKO 主干是完全的 UE Mannequin 命名（pelvis / spine_01~03 / clavicle_l / upperarm_l / lowerarm_l / hand_l / thigh_l / calf_l / foot_l / ball_l / toe_l，本次实测确认）。

这意味着 UE5 IK Retargeter 可以直接用，白拿四件它正在手写重造的东西：
  • Edit Retarget Pose —— 就是它方案里 Q（绕 Z 180°）与 K（逐骨基准差补偿）的可视化版本；
  • Chain Scaling = Globally Scaled —— 按源/目标骨长比自动缩放（我们实测腿长差 4.4%、臂长差 0.1%，正好需要分链）；
  • Stride Warping —— 步幅自动适配腿长，正对"滑步"；
  • Speed Planting（配 MotionExtractorModifier 生成脚速曲线）—— Epic 官方的滑步标准解法。
Gemini 全篇只走自研 Blender 管线，等于放弃了官方维护的步幅与脚部方案，全部自己造。另外它也没提到两条降维路径：
· Aventurine: League Tools —— 原生读写 .anm，绕开 glTF 骨骼朝向污染（正是「matrix_local 平均差 84.9°」的根源）；
· 2XKO 本体可解包（UE5.4），Darius 的第三人称动画真实存在（darius_base_nav_std_*）——locomotion 用它 = 零重定向误差。

4. 值得吸收的优点（这些比我的上一版做得好）

它的做法为什么值得吸收
双手主从武器约束 + 斧柄副握插槽（Master-Slave Weapon IK + Socket_LeftHand_Grip） 我上一版确实漏了。2XKO 只有 weapon_jnt_r 一个武器骨，源侧左手又没有独立握持信息。这是第三方称特写最容易露馅的点，必须补进计划
风险矩阵的「根因与案发表现 / 防御与解决策略」三段式比单纯列风险可读性强，便于逐条验收
验收门禁的"一票否决"形式（G1~G5，不过不许进下一阶段）与项目铁律 0.1 完全一致，形式正确
阶段划分里明确写出产出脚本名（blender_55_retarget_v5.py）可执行性强，便于排期
「绝不靠整体放慢播放速度掩盖滑步」正确且重要，值得写进规范

twist flip 的"退化时以大臂/大腿平面作滚转锚点"方向正确（虽然没定位到源侧 Upper/Lower 双骨这个真因）
