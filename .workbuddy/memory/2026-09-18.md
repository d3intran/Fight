## 神王战斧手持显示缺失 —— 定位与修复

### 现象
角色手中只剩"握柄 + 尾端小月牙"，77cm 大斧刃完全不可见。
初判（用户与我）：「之前修身下斧头黑影时误删了斧头主体」。

### 结论：初判错误，几何一次都没被删
硬证据链：
1. **顶点计数**：2XKO 源 FBX 的 `darius_godking_mesh_LOD0.007` = 5661 顶点 / 4698 面；
   导出的 `SM_Darius_GodKing_Axe.fbx` 完全一致；UE 资产 LOD0 = 5668（+7 为 UV/法线拆分）。
   沿长轴直方图**逐 bin 一致**。
2. **材质链路**：`M_Darius_Master` = BLEND_OPAQUE / 无双面 / 无 OpacityMask；`MI_Darius_Axe` 无覆盖。
3. **无遮挡对照**：把同 SM 用手部世界变换单独摆进场 → **完整斧头**。
4. **世界坐标核算**：斧头局部 +86（大刃端）→ (31.4, −3.7, **167.5**) = **胸腔内部**；
   局部 −86（尾钩端）→ (−14.2, −122.6, 52.2) = 体前膝下（就是截图里那截月牙）。
5. **A/B 隐藏**：隐藏 `WeaponAxe` 组件画面不变；隐藏就地 clone 则手中物体消失。

### 真因
- `blender_split_weapon.py` 的 `grip_z = min_v.z + size_v.z * 0.35` **用错轴**（斧头长轴是 Y，Z 只有 77cm 刃高）
  ⇒ pivot 落在**刃根**，手握手柄正中变成手握刃根，86cm 大刃整根外伸。
- `hand_rSocket.relative_rotation` 是试出来的 `(90,0,0)`（实测世界 (6.67,165.06,−137.52)）
  ⇒ 方向刚好把大刃送进躯干。

### 修复（只改 6 个数字）
`hand_rSocket`:
- `relative_rotation`: (90,0,0) → **(−106.334, −70.982, 9.342)**
- `relative_location`: (0,0,0) → **(0.18965, 0.10080, 0.00982)**（bone 空间，≈21.5cm 世界）
- `relative_scale` 保持 (0.01,0.01,0.01)；几何 / 材质 / 材质槽 / BP 结构全未动。

求解方法：目标世界朝向（局部 X→世界 +X，局部 Y→上倾 15°）→ **实测标定组合顺序**
（`World = Compose(Rel, Parent)`，残差 0.000000 vs 5.508537）→ 坐标下降残差 1.3e-07。

### 新踩的坑（已写入 AGENTS.md §5）
1. `unreal.Rotator` 位置参数顺序是 **(roll, pitch, yaw)** —— 历史上所有自动化截图相机朝向都是错的。
2. socket 相对旋转组合顺序是 `Compose(Rel, Parent)`，与直觉相反。
3. 该版本 `MathLibrary` 缺 `invert_rotator` / `rotate_vector` / `quat_from_rotator` → 用纯数值求解。
4. `HighResShot` 静默失败 + 一次只认最后一条 + 落地延迟 1~4 分钟；
   **`SceneCapture2D` + `export_render_target` 才稳**（输出无扩展名 HDR，用 ffmpeg 转 LDR）。
5. 直接改组件的 `relative_location` 会让它脱离 socket 挂载（世界变换退化成单位阵）。
6. `EditorAssetLibrary.unload_asset` 不存在。
7. FBX↔UE 局部轴语义翻转（大刃 FBX 在 −Y、UE 在 +Y），包围盒 Y 对称所以数值分辨不出。

## LOL 俯视角动画 → 2XKO 第三人称模型 · 重定向实施计划

产出：`Docs/Retarget/LOL_to_TP_Retarget_Plan.html`（含资产实测数据、外部调研、7 阶段计划、难点/风险/验收）

### 本次实测的硬数据（重要，后续复用）
- **源 LOL skin15 骨架**：179 骨，但真身体链仅 ~30；其余是 `Lion_*`（四足）、`Throne/L_Throne/R_Throne/Gem/Piece_1~3`（王座道具）、`*Buffbone*`（VFX 挂点）
  → **必须白名单裁剪**。源侧 twist=0 / ik=0 / ctrl=0，是纯 FK 形变骨。
- **源侧两个陷阱**：
  1. 膝/肘是 **Upper/Lower 等长双骨**（`L_Hip(48.84) → L_KneeUpper(48.84) → L_KneeLower(50.63)`；`L_Shoulder(40.54) → L_ElbowUpper(40.54) → L_Elbow(22.04)`）→ 三点链几何帧易退化，是腿部 17~22° 残留的嫌疑。
  2. `L_Foot` / `L_Toe` 是 **0.014 的微骨** → 踝点必须改用 `L_KneeLower.tail`，否则「脚长」算出来是荒谬值。
- **目标 2XKO 骨架**：309 骨，主干**完全兼容 UE Mannequin 命名**（pelvis/spine_01~03/upperarm_l/…）→ UE IK Retargeter 自动链映射可直接命中。
  有 24 根 twist 骨（源侧无对应）、~150 面部骨、`cape_chain_*`、`kneepad_jnt_*`/`ankle_front|back_jnt_*`、`weapon_jnt*`。
- **比例对照（全局缩放 = 1.8502/187.2095 = 0.009883）**：

| 度量 | 比值 | 相对全局偏差 | 后果 |
|---|---|---|---|
| 腿长/身高 | 0.0094 | **−4.4%** | 目标腿短 → 步幅偏大 → 滑步 |
| 上臂/前臂 | 0.0087 / 0.0114 | −12% / +15% | 肘点前后错位 |
| **髋宽** | **0.0077** | **−22%** | 大腿起点内收 → 走姿夹腿 |
| **颈长** | **0.0182** | **+84%** | 头会浮高 |
| 臂长/身高 | 0.0099 | +0.1% | 手臂几乎完美 |

  ⇒ **不是各向同性缩放**，必须「全局 + 分链 + 逐关节」三层补偿。
- 源动画：30fps、单动作极短（run 29 帧）、**in-place**；LOL **没有 walk**，只有 run/run_fast/run_homeguard。
- 美术风格：LOL 俯视角动画**为可读性整体前倾 + 夸张幅度 + 两姿态**（Riot 官方说法："exaggerate motions and tilt models for visibility"）→ 这是第三人称下「不自然」的最大来源。

### 工具调研结论
- **UE5 IK Retargeter** = 主力推荐。自带 Retarget Pose 对齐 / Chain Scaling(Globally Scaled) / Stride Warping / **Speed Planting**（配 MotionExtractorModifier 生成脚速曲线修滑步）。
  官方经验法则：FK Translation Mode 用 **Globally Scaled**；腿链**只到踝不到 ball**、Chain Depth=2；Pelvis 的 Blend to Source Translation=1.0 但 **Z 权重设 0**。
- **Aventurine: League Tools**（RitoShark，GPLv3，Blender 4.0+）= 原生读写 .skn/.skl/.anm + 内建 LoL Retarget + Wiggle2 布料物理。
  ⚠️ 本机 Blender 5.2 兼容性未验证。价值：**绕开 glTF 骨骼朝向污染**（正是「matrix_local 平均差 84.9°」的根源）。
- **Cascadeur 2026.x**：AutoPhysics / Motion Cleaning(fulcrum 脚锁) / Animation Unbaking / Secondary Motion，支持 UE5.8 LiveLink。
  ⚠️ 免费档限 300 帧 / **120 关节** → 目标 309 骨用不了，只能用在裁剪后的源骨架上；FBX 导出需 Indie($19/月)。
- **2XKO 本体可解包**（UE5.4，umodel/FModel）：**Darius 的第三人称动画真实存在**，如 `darius_base_nav_std_walk_forward`、`darius_base_msc_taunt_respect`，路径 `Champions/Darius/Champ_Darius/Content/Base/Meshes/`。
  ⇒ **降维打击路线**：locomotion 用官方同源动画（零重定向误差），LOL 动画只用于技能。

## Gemini 重定向方案评审（基于实测校准）

产出：`Docs/Retarget/Gemini_Plan_Review.html`

### 本次新增的三条硬实测（重要，推翻了一个流行说法）
**先锚定前后方向**：`plan_04_facing.py` 用两个独立锚点定死 —— **披风链在 +Y（身后）、斧刃在 −Y（身前）** ⇒ **forward = −Y**。

**然后逐动作量倾角（相对 bind pose，正=前倾）**：

| 动作 | 躯干轴 | 颈段 | 头骨轴 | 判读 |
|---|---|---|---|---|
| bind | −7.6° | +7.2° | 0.0° | 基准 |
| **idle1** | **+0.4°（不动）** | **−32.1°** | **−12.1°** | 后仰全在颈+头 ≈ **44°** |
| idle2 | −0.3° | −35.1° | −15.2° | 同上 |
| **run** | **+34.3°** | **+52.3°** | +10.8° | **累计 ~86° 前冲** |
| **run_fast** | **+61.9°** | **+63.8°** | +22.4° | **累计 ~126°，几乎趴平** |
| run_homeguard | +52.4° | +65.7° | +11.3° | 同上 |
| attack1 | −18.3~+54.3 | −8.5~+69.4 | −23.6~+1.7 | 大幅摆动，设计意图 |
| idlen | +38.7（中位） | +29.8 | −2.8 | 战斗前倾 |

**结论（纠正一个广泛流传的说法）**：
- ❌「LOL 为了俯视让**脊柱**后仰 15~30°」→ **错**。脊柱在 idle 里**零位移**；后仰是 **`Neck` 骨 −32° + `Head` 骨 −12°**。
- ❌「LOL 动画整体后仰」→ **错**。idle 是抬头，**run/run_fast 是大幅前倾**（第三人称下会像"趴着跑"）。
- ⇒ 去倾斜不能统一反向补偿：**idle 只动 neck/head（spine=0）；run 家族动 spine（−15°~−45°）+ neck（−25°~−55°）；attack/spell 不做去倾斜只做限位压缩。**
- ⇒ 现有 v4 的权重（spine_01 45%/spine_02 35%/spine_03 20%/neck −60%）**分配是错的**（给 spine 太多），Gemini 改成 30/35/25/−60 同样无出处。正确做法是**逐动作实测反解**。

### 其它实测校准
- **身高**：目标网格 z 上限 **2.06 m**，不是 2.47 m（AGENTS.md 里那句"放到 2.47m 长腿上"是未核实的旧注，需修正）。
- **体型方向**：腿长/身高 LOL **0.5281** > 目标 **0.5050** —— LOL 的腿相对**更长**；臂长比几乎相同。真正的比例陷阱是**髋宽 −22%、颈长 +84%**，不是"短腿对长腿"。
- **源动画规格**：46 个动作，attack1 = 2.433s(73帧) / spell1 = 0.533s(16帧)，**"前摇 1~2 帧"是修辞**；`spell4_5`、`turn_l/r` 确实存在。
- **LOL 没有 walk**（只有 idle1/idle2/idlein/run/run_fast/run_homeguard）。

## 重定向最终计划定稿

产出：`Docs/Retarget/FINAL_Retarget_Plan.html`（取代此前所有版本）

### 本轮发现并修正的三处（含对我自己的修正）
1. **「Idle→Run 折颈暴冲」是真问题，且已量化**：按绝对角反解，颈部补偿 idle +29.9° → run −37.5°，**相差 67.4°**（与外部评审估的 67° 吻合）。idle→run_fast 相差 75.9°。
2. **但「烘焙进 FBX 会抽搐、放运行时层就不会」这个论证不成立**：淡化插值的是姿态，差 67° 就是 67°，与偏置来自哪里无关。
   **运行时层的真正价值**：① 提供施加阻尼的钩子（Inertialization/Spring）；② **让偏置能随运行时速度连续变化**（离线烘焙做不到）。
   ⇒ **定案：把偏置定义成 `offset(speed)` 连续曲线（自变量 = M0 实测的动画隐含速度），这才是根治方案。**
3. **两处我自己的表述需要修正**：
   - 「颈长 +84% 会导致头浮高」→ **不准**。旋转传递下头高由目标自身骨架决定。**真实后果：同样大小的颈部旋转，目标头部前后位移被放大 1.84 倍**（run 的颈段 59.5° 会把头甩出去）。
   - 我此前给的「thigh 加 6°~8° 外展偏移」**也是无出处魔数，作废**。改为：先在 Retarget Pose 里对齐站姿，仅当实测膝间距比偏差 > 10% 才加偏移。

### 定稿管线
`DCC 净化 → UE IK Retargeter → Control Rig 运行时层 → 门禁验收`
- 去倾斜 = **速度连续偏置曲线**（躯干 v=0→+5.2°、v_run→−8.7°、v_fast→−32.3°；颈 v=0→+29.9°、v_run→−37.5°、v_fast→−46.0°），idle 只还原 **70%**（保留睥睨气质）
- 步幅：以目标移速（500~600）为锚 + Stride Warping；**G3b 速度闭环一票否决**
- 里程碑：**M0 尺子(0.5d) → M1 垂直切片 idle+run(3.5d) → M2 全量动作与风格(4d)**，合计 8 天
- 门禁：G1 朝向 / G2 关节位置 / G3a 局部脚滑 / **G3b 速度闭环** / G4 视线(只约束慢变基线 + 偏置标准差<4°，非逐帧硬约束) / G5 生理限位且幅度保留≥85% / **G6 融合平滑(角速度连续、峰值<600°/s)** / G7 双手握斧+穿模
- 第一步：`plan_10_src_clean.py`（源骨架净化，179→~45 骨）
